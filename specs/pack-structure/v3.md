# Pack Structure v3 规格说明（现行 · v3 r2）

> 状态：**现行（v3 r2）**。r2 = 2026-09 修订：新增可选顶层目录 `vendor/` 承载 vendored 依赖 tarball（§8，配合 manifest v5 r2 的 `vendored{}` / `offline`；配套 RFC `rfc-vendored-payload-and-offline-packs.md`）。`.dspack` v3 容器 = **纯 ZIP 内核 + 根 `dspack.json` 标记（version 3，不变）**，**统一承载两种形态**——`type:"profile"`（单 profile，`overrides/` 落 profile 根 + 可选 `home/` 落 home 根）与 `type:"dshhome"`（整个 DSH_HOME，`overrides/` 按 home 根平铺）。承载 manifest v5（`../manifest/v5.md`）。生成侧 `dsh-packforge-app` 与参考实现 `all-about-whales` 均以 `.dspack` v3 产出。r2 为严格超集：无 `vendor/` 的包与 r1 行为完全一致。
>
> 关联：`../pack-structure/v1.md`（历史 `.tgz`）、`../pack-structure/v2.md`（历史单 profile `.dspack`，无 `home/`）、`../manifest/v5.md`（本文容器的索引契约）。

---

## 1. 概述

v3 把 v2 的「单 profile `.dspack`」推广为「统一容器」，在 v2 的 `overrides/`（profile 根覆盖）之外新增两个概念：

- **`home/` 目录**（profile 形态可选）：单 profile 整合包也能携带「上一级目录」（`$DSH_HOME` 根）的内容，如全局 skill / `.agent-presets`。
- **dshhome 形态**：`overrides/` 的覆盖目标从「单个 profile 根」提升为「整个 `$DSH_HOME` 根」。

容器本身是标准 ZIP（`PK\x03\x04` 开头）；「是不是 dspack、容器版本」由根 `dspack.json` 承载。

---

## 2. 容器与标识文件

### 2.1 文件名

```
<manifest.name>-<manifest.version>.dspack
```

### 2.2 标识文件 `dspack.json`（ZIP 根，必有）

```json
{ "format": "dspack", "version": 3 }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `format` | string | 固定 `"dspack"` |
| `version` | number | 容器格式版本，统一为 `3`（profile 与 dshhome 共用） |

**加载器判定（同 v2）：**

1. 按标准 ZIP 打开（首两字节 `PK`）；
2. 读根 `dspack.json`：缺失 / 非对象 → 不是 dspack → 拒载；
3. `format` ≠ `"dspack"` 或 `version` ≠ 3 → 报「不支持该 `.dspack` 版本」；
4. 通过 → 按 manifest `type` 分形态处理（§3）。

## 3. 归档内部布局（两种形态）

### 3.1 profile 形态（manifest v5 `type:"profile"`）

```
<name>-<version>.dspack
└── ZIP 内:
    ├── dspack.json            # ★ version 3
    ├── manifest.json          # ★ v5（type: profile）
    ├── package.json           # profile 机器文件（可选快照，被 manifest 权威重建）
    ├── pnpm-workspace.yaml    # 可选
    ├── pnpm-lock.yaml         # 可选
    ├── overrides/             # → $DSH_HOME/profiles/<name>/（profile 根）
    │   ├── cordis.patch.yml
    │   └── ...
    └── home/                  # → $DSH_HOME/（可选，上一级目录内容，见 §5）
        ├── skills/<name>/SKILL.md
        └── .agent-presets/<id>/agent.cordis.yml
```

### 3.2 dshhome 形态（manifest v5 `type:"dshhome"`）

```
<name>-<version>.dspack
└── ZIP 内:
    ├── dspack.json            # ★ version 3
    ├── manifest.json          # ★ v5（type: dshhome）
    ├── package.json           # 可选（defaultProfile 快照）
    ├── pnpm-workspace.yaml    # 可选
    ├── pnpm-lock.yaml         # 可选
    └── overrides/             # → $DSH_HOME/（home 根，按相对路径平铺）
        ├── AGENTS.md
        ├── profiles/<name>/cordis.patch.yml
        ├── .agent-presets/<id>/agent.cordis.yml
        ├── skills/<name>/SKILL.md
        └── data/...
```

> 关键约定：**ZIP 根必须包含 `dspack.json` 与 `manifest.json`**。用户内容进 `overrides/`（profile 形态）或 `overrides/` + `home/`（profile 形态带上一级目录）。

## 4. 归档内容清单

| 类别 | 文件 | 说明 |
| --- | --- | --- |
| 必有 | `dspack.json` | 容器标记（`format` / `version` 3） |
| 必有 | `manifest.json` | v5 契约头（`type` 决定形态） |
| 可选 | `package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml` | 机器文件 / 设置 / 传递依赖锁定 |
| 必有（目录） | `overrides/` | 用户文件（落点随形态，见 §3） |
| 可选（目录） | `home/` | 仅 profile 形态：上一级目录内容（见 §5） |
| 可选（目录） | `vendor/` | vendored 依赖 tarball（v3 r2，见 §8） |
| 不打包 | `node_modules` 等 | 依赖由 `pnpm install` 重建；重内容走 `files[]` / `skills[]`；上游消失 / 从未发布 / 离线场景的依赖走 `vendor/`（§8） |

## 5. `home/` 目录（profile 形态的「上一级目录」）

`home/` 是**单 profile 整合包携带 home 级内容**的载体：

- `home/xxx` → 安装时写到 `$DSH_HOME/xxx`（**不是 profile 根**）；
- 例：`home/skills/<name>/SKILL.md`、`home/.agent-presets/<id>/agent.cordis.yml`、`home/AGENTS.md`；
- 语义与 `overrides/` 一致：**文件级复制替换**，不做字段级合并；
- 安全过滤同 `overrides/`（§9）。

> 为什么需要 `home/`：skill（`$DSH_HOME/skills`）、agent-preset（`$DSH_HOME/.agent-presets`）在 DSH 里是 **home 级**（profile 目录的上一级），不在单个 profile 目录内。`home/` 让 profile 整合包也能顺带分发这些全局单元，而不必升级成整个 dshhome 快照。

---

## 6. `overrides/` 语义

`overrides/` 是「随包携带、安装时写到目标根」的目录，落点随形态：

- **profile 形态**：`overrides/xxx` → `$DSH_HOME/profiles/<name>/xxx`；
- **dshhome 形态**：`overrides/xxx` → `$DSH_HOME/xxx`。

「覆盖」是文件级复制替换，不是语义合并；真正的「合并式覆盖」由 `cordis.patch.yml`（Cordis 补丁层）承担。

### dshhome 形态的四类单元落盘

| 单元 | `overrides/` 内 | 安装落点 | 依赖坐标层 |
| --- | --- | --- | --- |
| profile | `profiles/<name>/cordis.patch.yml` 等 | `$DSH_HOME/profiles/<name>/` | ✅ `dependencies`（manifest 权威重建） |
| preset | `.agent-presets/<id>/agent.cordis.yml` + `preset.yml` | `$DSH_HOME/.agent-presets/<id>/` | ❌ 纯文件 |
| skill | `skills/<name>/SKILL.md`（+ 资源） | `$DSH_HOME/skills/<name>/` | ❌ 纯文件（重技能走 `skills[]`） |
| 全局指令 | `AGENTS.md` | `$DSH_HOME/AGENTS.md` | ❌ 纯文件 |

---

## 7. files[] / skills[] 下载（重内容按需拉取）

- profile 形态：`files[]` 落 profile 根内；dshhome 形态：落 `$DSH_HOME` 内。
- 安装时逐个下载到 `path`，校验 `sha256` + `size`；任一失败 → 删除已下文件并整体回滚。
- 常规插件走 npm / git（`dependencies`），不进 `files[]` / `skills[]`。

## 8. `vendor/` 与 vendored 安装（v3 r2）

> 承载 manifest v5 r2 的 `vendored{}`（`../manifest/v5.md` §12；需求来源：[DSH-PackForge/DSH-PackForge#3](https://github.com/DSH-PackForge/DSH-PackForge/issues/3)）。RFC：`rfc-vendored-payload-and-offline-packs.md`。`vendor/` 是可选目录：无此目录的包（r1）行为与修订前完全一致。

### 8.1 布局与来源

```
vendor/
├── npm__dsh-pet/dsh-pet-0.2.0.tgz
└── github__DViridescent__dafy-whale-theme/dafy-whale-theme-99e8c57.tgz
```

- **tarball 来源**：npm 坐标 = registry 分发原件；git 坐标 = `git archive <sha>` 产物（tar 内路径以 `package/` 前缀为准，与 npm tarball 对齐）。**有上游原件且未修改时，字节一致、不改写**。上游无原件（未发布 / 已消失）或作者持有**本地修改版**（如魔改插件——屏蔽 manifest url 绕过自动更新的那类，见 #3）时，按 npm tarball 规范本地打包：tarball 哈希以包内实际内容为准（自洽），`reason` 记 `"unpublished"` / `"local-modified"`；统一算法下本地命中即作者意图。
- **目录名编码（建议性，非权威）**：坐标中 `:` `/` `@` 替换为 `__`；**manifest `vendored[].path` 才是权威**，安装端不解析目录名反推坐标。
- 为什么嵌 tarball 而非展开的 node_modules：pnpm 的 node_modules 是符号链接 + `.pnpm` 虚拟店布局，ZIP 往返即坏；tarball 正是 `pnpm install` 的拉取单元；单 tarball 单哈希，完整性最强。

### 8.2 安全过滤例外

- `vendor/` **豁免**「嵌套压缩包」过滤；`vendor/` **之外**，§9 四类过滤原样适用；
- `vendor/` 内**只允许 `.tgz`**；每个 tarball 必须能在 manifest `vendored` 中按 `path` 找到条目并逐一通过 `sha256` + `size` 校验；未登记文件或哈希不符 → 拒装；
- 解包后施加**凭据/敏感内容扫描**（命中即拒绝该依赖并报错，不静默剔除——剔除会改变内容哈希）与**路径穿越校验**（拒绝 `..` 越界路径）。

### 8.3 安装决策与统一算法

**统一算法（规范定义：单一路径，无模式开关）**：

```
vendor/ 存在?
  → 阶段 0 已逐 tarball sha256 校验
  → 预填充本地 pnpm store(或本地 registry,实现自选)
  → pnpm install --prefer-offline
```

- 本地命中的坐标直接用副本，未命中 / 无副本的走 registry——**本地与网络自动互为兜底**，不存在「失败 → 重建 → 重试」分支：死上游依赖第一遍就命中本地 store；
- **无模式字段**：本地 / 云端的时机由算法统一决定，manifest 不声明（`fallback` / `prefer` / `offline` 字段已在 r2 定稿前删除——tarball 与上游字节一致，本地优先与云端优先结果相同，模式声明是冗余）；
- **严格离线是启动器自选行为**：检测到 `vendored` 覆盖完整闭包（对照 `pnpm-lock.yaml`）时可改用 `pnpm install --offline`（零网络、缺件即报错）；「离线可装」是覆盖完整性派生的属性，不是包的声明。

**覆盖范围 × 行为对照**：

| `vendored` 覆盖（作者决定） | 统一算法下的实际行为 |
| --- | --- |
| 局部覆盖（部分坐标） | 覆盖内命中本地，其余走云端（混合分发） |
| 全量覆盖（含传递闭包） | 离线可装；在线机器上同样一次装完 |

**直挂（direct-mount）——无传递依赖叶子包的轻量替代**：tarball 校验后 `tar -xzf --strip-components=1` 直接解进 `node_modules/<pkg>`，绕过 store；**必须**同时把该坐标从写入 profile `package.json` 的依赖中剔除（安装器改写，manifest 不动——否则 pnpm 仍会尝试从 registry 拉取）。**限制**：直挂不安装该包自身的传递依赖，带依赖的包必须走统一算法（DSHL 方言即直挂路线，故其包均为叶子插件）。

失败回滚沿用 §10 语义。git 坐标以 tarball（`file:` 引用或发布进本地 registry）替代 git 拉取。

### 8.4 launchers 判定（v5 r2）

安装端按 manifest `launchers`（`../manifest/v5.md` §14，条目先归一化为全式）判定，**警告放行、不硬拒**：

| 条目 / 查表结果 | 行为 |
| --- | --- |
| `supported:true`，无 `minVersion` | 静默安装 |
| `supported:true`，本启动器版本 ≥ `minVersion` | 静默安装 |
| `supported:true`，版本不足 / 版本未知 | 轻提示（「需要 <id> ≥ <ver>」）→ 放行 |
| `supported:false` | 重警告（显示 `reason`）→ 放行 |
| 未列出，map 无任何 `supported:true`（纯黑名单） | 静默安装 |
| 未列出，map 有 `supported:true`（白名单） | 轻提示（「声明支持：<列表>」）→ 放行 |

放行须在安装日志留痕（「用户已确认继续」）。**版本比较规则**：按 `.` 分段、逐段数值比较、缺段视为 `0`；不做 rc 等预发布语义。启动器须自报版本号（`../launcher-registry.md`）。

### 8.5 方言互操作（DSHL `vendor:` 语法）

PCL-Deepseek-Harness-Launcher（DSHL）已在野外产出「`dependencies` 值 = `vendor:<file>.tgz` + `vendor/vendor.json`（`packages[]: { file, name, sha256 }`）」形态的方言包。互操作纪律：**消费宽容，生产禁止**。

- **安装器（消费侧）**：遇到上述方言形态时，按**隐式 vendored 条目**消费——从 `vendor/vendor.json` 按 `file` 找条目、验 `name` 一致与 `sha256` 后按 §8.3 安装，不传给 pnpm；与显式 `vendored{}` 并存时**显式条目优先**。
- **生成器（生产侧）**：**禁止**产出方言——`dependencies` 值必须是精确版本 / commit sha；vendoring 一律走 `vendored{}`。校验器对生成器产出检查此条，对安装器输入不检查。

## 10. 安装端行为

> **完整导入流程（阶段划分、r2 决策分支、回滚语义、老启动器行为）以 `../manifest/v5.md` §11 为准**；本节保留容器侧的两形态落点速查。r2 分支：`dshVersions` 交集决策、`vendor/` 回退与离线安装（§8.3）、`launchers` 警告放行（§8.4）。

**profile 形态**：

1. 解 ZIP → 校验 `dspack.json`（v3）→ 读 manifest（v5、`type:"profile"`）；
2. `overrides/` 覆盖到 profile 根 → 安装 `dshVersion` → `pnpm install` → `reconcileProfile`；
3. `home/`（若有）覆盖到 `$DSH_HOME` 根；
4. `files[]` 下载 + 校验，失败回滚。

**dshhome 形态**：

1. 解 ZIP → 校验 `dspack.json`（v3）→ 读 manifest（v5、`type:"dshhome"`）；
2. 校验 `profiles` 非空、不含 `web` / `headless`，`defaultProfile` 存在；
3. **先确保 `dshVersion` 的 DSH 已安装**；
4. 建实例 `$DSH_HOME`；
5. **逐 profile**：`overrides/profiles/<name>/` 落盘 → `pnpm install` → `reconcileProfile`（各自独立）；
6. home 级 `overrides/` 其余内容落盘；
7. `files[]` / `skills[]` 下载 + 校验，失败回滚；
8. `defaultProfile` 设为默认。

## 11. 与 v1 / v2 的关系

| 版本 | 容器 | 覆盖目标 | 状态 |
| --- | --- | --- | --- |
| v1 | `.tgz` | 单 profile（扁平快照） | **历史**（`pack-structure/v1.md`） |
| v2 | `.dspack`（v2） | 单 profile（`overrides/` → profile 根） | **历史**（`pack-structure/v2.md`，无 `home/`） |
| **v3** | `.dspack`（v3） | **profile（`overrides/` → profile 根 + 可选 `home/` → home 根）\|\| dshhome（`overrides/` → home 根）** | **现行**（本文） |

> v3 是 v2 的超集：profile 形态 = v2 + `home/`；dshhome 形态 = 覆盖目标提升到整个 home。索引与存储的「指针制」分工不随容器变化而改变。v3 r2 为增量修订（新增可选 `vendor/` 目录），容器版本号不变——`dspack.json` 仍为 `version: 3`（其在所有已部署加载器处是硬门禁）。

---

## 12. 结论

> `.dspack` v3 = **纯 ZIP + 根 `dspack.json`（version 3）+ 两种形态**：`type:"profile"` 用 `overrides/`（profile 根）与可选 `home/`（上一级目录）承载单 profile 及其全局 skill/preset；`type:"dshhome"` 用 `overrides/` 按 `$DSH_HOME` 根平铺承载整个工作环境。标准 ZIP 保证可直接打开，根标记保证版本演进，`home/` 让「单 profile 也能带全局单元」、dshhome 让「整个 home 可还原」——在 v2 之上的平滑演进，模仿 mrpack 而不失 DSH 的层栈与 home 契约。
